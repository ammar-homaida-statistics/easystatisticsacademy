Exercise 4.3 — Rounding Numbers for Reports

Rounding looks like the simplest step of a report. Yet R and Python round 2.5 down to 2, Excel rounds it up to 3, and 2.675 rounds to 2.67 everywhere a computer stores it in binary.

1 Goal

By the end of this exercise you will be able to:

  1. predict how R and Python round values ending in 5;
  2. explain why some values seem to round the wrong way;
  3. round half away from zero when a rule requires it, and know its limits.

2 Predict first

Before running anything: what does each line return?

R

round(c(0.5, 1.5, 2.5, 3.5))
round(2.675, 2)

Python

print(round(2.5), round(3.5))
print(round(2.675, 2))
Show the answer

Both languages round a value exactly halfway to the nearest even digit, so 0.5 → 0 and 2.5 → 2:

[1] 0 2 2 4
[1] 2.67
2 4
2.67

And 2.675 becomes 2.67, not 2.68, in both.

3 The idea

Round half to even ("banker's rounding", the IEEE 754 default) rounds an exact tie to the even neighbour. Over many values, half the ties go up and half go down, so sums and means are not pushed upwards. Excel, SPSS's RND and most school textbooks instead round half away from zero (2.5 → 3).

A second effect has nothing to do with the rule: 2.675 cannot be stored exactly in binary (Exercise 1.3). The stored value is 2.67499999999999982…, which is below the tie, so every method rounds it to 2.67. Only decimal arithmetic on the text "2.675" gives 2.68.

4 Your task

Round half away from zero

Write a rounding function that rounds halves away from zero, so that 0.5, 1.5, 2.5, 3.5 become 1, 2, 3, 4. Then apply it to 2.675 with 2 decimals and explain the result.

R — starter code

# Your code: round_half_up <- function(x, digits = 0) { ... }

Python — starter code

# Your code: def round_half_up(x, digits=0): ...

5 Hints

Hint 1

Shift the decimal point, add 0.5 to the absolute value, take floor(), shift back, and restore the sign.

Hint 2

Python's decimal module has a rounding mode ROUND_HALF_UP; create the Decimal from a string, not from a float.

6 Solution

Show the solution

R

round_half_up <- function(x, digits = 0) {
  m <- 10^digits
  sign(x) * floor(abs(x) * m + 0.5) / m
}
round_half_up(c(0.5, 1.5, 2.5, 3.5))
round_half_up(2.675, 2)              # still 2.67: stored as 2.67499...

Output

[1] 1 2 3 4
[1] 2.67

Python

from decimal import Decimal, ROUND_HALF_UP

def round_half_up(x, digits=0):
    q = Decimal(1).scaleb(-digits)            # 1, 0.1, 0.01, ...
    return float(Decimal(str(x)).quantize(q, rounding=ROUND_HALF_UP))

print([round_half_up(v) for v in [0.5, 1.5, 2.5, 3.5]])
print(Decimal(2.675))                         # what is really stored
print(round_half_up(2.675, 2))                # decimal text "2.675"

Output

[1.0, 2.0, 3.0, 4.0]
2.67499999999999982236431605997495353221893310546875
2.68

The R function works on the stored binary value, so 2.675 still gives 2.67. The Python version converts the number to its shortest decimal text first (str(2.675) is "2.675"), so it gives 2.68. Neither is wrong; they round different numbers.

7 Check yourself

Your answer is correct if

  • 0.5, 1.5, 2.5, 3.5 become 1, 2, 3, 4 with your function;
  • you can explain why 2.675 gives 2.67 with binary values and 2.68 with decimal text.

8 Why it matters

Round once, at the end

Rounding rules matter when tables must match another program exactly, or when rounded values are added up (rounded percentages that sum to 99 or 101). The safer habit is to keep full precision through every calculation and round only the numbers you display, using one stated rule.
